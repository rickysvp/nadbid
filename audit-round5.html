一、智能合约审计（Foundry，23 测试全过）

P1

KolPass.burn 多人场景逆向选择套利（经济漏洞）

contracts/src/KolPass.sol:76-102
问题
burn 返还 = curvePriceAt(total - i)（最新供应递减）。单人 mint1→burn1 无套利（第 1 轮已修），但多人场景：A mint 1 枚（成本 ≈ 0.0000134 MON），B 大量 mint 推高曲线到供应 1001，A 再 burn 自己那枚 → 返还 ≈ 13.4 MON，净赚 ~12.3 MON（来源是 B 沉淀的资金）。先 mint 者可在供应被推高后低买高卖。
最小修复方向
burn 返还基准改为「该 token 铸造时的成本」而非「当前曲线价」，需在 mint 时记录每 token 的 mintPrice；或禁止 burn（soulbound 全禁）改用「持有即权益」模型；或 burn 设冷却/限额。需产品决策。
P1

settle 依赖外部转账成功，拒收地址致资金永久卡死

contracts/src/KolAuction.sol:88-104
问题
settle 把 20% 转 platformTreasury、80% 转 kol，require(ok1/ok2)。若任一是拒收合约（无 receive/回退失败），settle 永久 revert → 拍卖资金锁死。且 requestBondRedeem 要求名下全部拍卖 settled（NadbidRegistry.sol:62-64）也被连带 block → KOL 的 10 MON 担保金永不可赎回。
最小修复方向
① 创建拍卖时校验 kol/treasury 为可接收地址（或校验 isContract 时必须有 receive）；② settle 改为「记录待领金额 + 分开领取」的 pull 模式，避免单点失败阻断全部；③ 或对转账失败提供「标记失败 + 允许重试指定接收方」的逃生口。
P2

Registry 封禁功能是死代码（banned 只读不可写）

contracts/src/NadbidRegistry.sol:26,84,105-108
问题
banned mapping 仅被 isKolBanned/canCreate 读取，全合约无任何函数能置 true（无 ban/unban、无 onlyOwner setter）。KolAuction.placeBid 里的 BANNED 检查形同虚设——恶意 KOL 永不可被封禁。
最小修复方向
给 Registry 加 onlyOwner 的 setBanned(address,bool)，并可考虑同步触发已创建拍卖的冻结（需 KolAuction 增加 owner 校验）。
P2

registerKol 链上无身份绑定，X 身份与钱包无关联

contracts/src/NadbidRegistry.sol:39-46
问题
任何地址调 registerKol(handle, followers)，只要 followers ≥ MIN_FOLLOWERS 即注册成功。合约无法验证 X 真实性——攻击者可绕过前端直接调合约注册任意 handle（含冒充知名 KOL）或虚报粉丝数。
最小修复方向
OAuth ticket 在签发时绑定钱包地址（ticket 内嵌 wallet），verify-ticket 校验 wallet 与当前连接一致后再签名提交链上；或 registerKol 增加链上签名承诺（对 X 身份哈希做 EIP-712 签名）。属信任模型设计缺口，需产品决策。
P3

createKolPass 无「每 KOL 一个」限制；createKolAuction content/duration 无上限

contracts/src/NadbidFactory.sol:20-45
问题
KOL 可无限创建 PASS 合约（Registry.passContracts 无限膨胀）；超长 content（string 存链上）推高 gas 甚至 OOG；duration 无上限可造「永不结束」的拍卖。前端 textarea 也无 maxLength。
最小修复方向
createKolPass 加「已创建则拒绝」或「仅首枚免费/其余收费」；createKolAuction 对 content 长度（如 ≤200 字符）与 duration 上限（如 ≤24h）加 require；前端同步 maxLength 与校验。
P3

burn 前端实际不可用（无 tokenId 枚举能力）

src/components/kol-profile/MintBurnPanel.tsx:99-100
问题
KolPass 未继承 ERC721Enumerable，无 tokenOfOwnerByIndex；前端 ABI 无 tokenId 枚举 → 用户无法列出并选择要 burn 的 token，Burn Tab 一直是「提示 + 置灰」。用户当初明确要求 burn 能力。
最小修复方向
KolPass 继承 ERC721Enumerable（或维护 ownerTokenIds 数组），前端遍历列出 tokenId 供选择。涉及合约重部署。

二、钱包连接 / 身份 / 前端交互

P1

页面内钱包连接走 mock，链上写入必然失败（假连接陷阱）

src/components/trade/ConnectModal.tsx + src/pages/KolOnboardingPage.tsx:347 + src/stores/walletStore.ts:99-114
问题
Onboarding「Connect Wallet」按钮、拍卖详情出价弹窗、Mint 弹窗、Claim/Staking/Arbitration 都调用 useWalletStore().connect()（mock：假地址 0x4F8a... + 假余额 12450 MON），不触发 wagmi 真实连接。用户点后 walletStore 显示「已连接」但 wagmi useAccount 仍 disconnected → 后续所有链上写入（registerKol/placeBid/mint）必然失败。全应用只有顶栏 components/wallet/ConnectButton 是真实 wagmi 连接入口。
最小修复方向
把 trade/ConnectModal 与 Onboarding 的 connect 改为复用 wagmi useConnect（即 wallet/ConnectModal 逻辑），或全局删除 mock connect 路径；mock 仅保留在 VITE_WALLET_MODE=mock 显式开启时。
P2

OAuth ticket 未绑定钱包地址（多钱包可共用同一 X 身份）

server/x-oauth.ts:90-95,242-258
问题
ticket 只含 username/followers/exp，不含申请者钱包地址。同一 X 账号完成 OAuth 后，ticket 在 URL 中传递，可被截获或转交他人 → 任意钱包用它注册该 X 身份。与合约 registerKol 无身份绑定叠加放大。
最小修复方向
x-auth-url 时由前端把当前钱包地址传给 server，ticket 内嵌 wallet；verify-ticket 校验 wallet 与请求方一致（用签名或 session）。
P2

Claim/Staking/Arbitration/Wallet 仍是 mock 占位，与「真实数据」偏好冲突

src/pages/{StakingPage,ClaimPage,ArbitrationPage,WalletPage}.tsx
问题
Staking 用 mockAvailableStakes/mockStakedPositions、Claim/Arbitration 用 mock 交易、WalletPage 显示 mock 质押/积分/历史。这些是核心功能页（导航可达），用户会误以为真的上链。与用户「测试网开发，不要模拟数据」的明确偏好直接冲突。
最小修复方向
要么接入真实合约（若 SP-2 有 Staking/Claim 合约），要么在页面上显著标注「MVP Preview / 未上链」，避免误导；优先隐藏或禁用入口。

P3

曲线预估与链上真实值存在偏差

src/components/kol-profile/MintBurnPanel.tsx:125-126 + src/utils/bondingCurve.ts:17-19
问题
前端 curvePriceAt(newSupply, effectiveSupply, effectivePrice) 把「当前点」当锚点，而链上锚点是固定的 (baseSupply=1000, basePrice)。供应量≠baseSupply 时，前端预估的 Est. New Price 与链上真实曲线价偏差可达数个百分点且随供应增加累积。链上 KOL 页未读取链上 curveConfig 驱动曲线图。
最小修复方向
链上路径用 useKolPass.curveConfig（真实 basePrice/baseSupply）计算 newPrice；或预估仅作展示并标注「估算」。
P3

estimateMintCost 时序竞争导致 value 可能不足

src/web3/hooks/useKolPass.ts:128-131
问题
curveConfig 已加载但 totalSupply 未就绪时回退 curvePrice × quantity（单币近似），高供应量下低估成本 → 链上 mint revert INSUFFICIENT。
最小修复方向
totalSupply 未就绪时禁用 mint 按钮或等待两查询都就绪。
P3

Mint 后余额刷新金额与实际扣款不符

src/components/kol-profile/MintBurnPanel.tsx:174
问题
链上 mint 后 wallet.refreshBalance(qtyNum * effectivePrice) 用单币价×数量刷新余额，未含 8% 手续费；应改用 Number(chainCostWei)/1e18。
最小修复方向
刷新金额对齐 chainCostWei（或 real 模式直接用链上余额查询，不传 delta）。

四、部署 / 配置（P2 提醒）

P2

Vercel 生产环境变量缺失风险

.env / vercel.json / server/app.ts
问题
server 端需在 Vercel 配置：X_FRONTEND_URL=https://nadbid.fun（OAuth 回调跳回 + CORS）、X_CALLBACK_URL=https://nadbid.fun/api/kol/x-oauth-callback（X App 登记的 callback 必须是它）、X_FOLLOWERS_THRESHOLD=1000（与合约 MIN_FOLLOWERS 一致，缺省默认 5000 会卡掉 1000-4999 粉丝 KOL）、X_STATE_SECRET、X_CLIENT_ID/SECRET。线上合约地址已是新值（已核验线上 JS 含 0x33b5de3e…/0xc299e1ee…），但若 X_FOLLOWERS_THRESHOLD 未设，线上验证会按 5000 走。
最小修复方向
在 Vercel 环境变量面板逐一核对上述项；尤其 X_FOLLOWERS_THRESHOLD 必须 =1000（与合约一致）。
